# Unity 动作游戏分层有限状态机（FSM）设计文档

## 1. 总体架构

角色状态机采用**三层分层有限状态机**，每层为一个独立子状态机，负责一个关注领域。各层通过统一的角色状态协调器进行优先级仲裁、动画混合和输入控制权分配。

- **基础层（Locomotion）**：Idle、Move、Jump、Sprint  
  负责角色的空间移动和基础运动状态，几乎持续运行。
- **攻击层（Attack）**：普通攻击(attack1 + attack2 2个动作)、技能Q、技能R  
  负责出招逻辑、连段、前摇后摇。激活时临时覆盖或约束基础层的行为。
- **受击层（Hit）**：受击硬直、击退、浮空、倒地、死亡  
  拥有最高响应优先级，可以打断其他层的绝大多数行为。

分层设计的核心优势在于避免状态组合爆炸（如 `JumpAttack`、`MoveSkillQ`），各层独立演化，通过协调器组合出完整的角色表现。

## 2. 各层状态定义

### 2.1 基础层（Base Layer）

| 状态 | 说明 |
|------|------|
| Idle | 站立待机，可响应移动输入和其他层覆盖。 |
| Move | 地面行走/跑动，由玩家输入驱动。 |
| JumpStart | 起跳动作，短时间不可取消，包含蹬地动画。 |
| JumpAir | 空中状态，可循环混合上升/下落姿态。 |
| JumpEnd | 落地缓冲，播放落地动画并可含短暂硬直。 |
| Sprint | 冲刺/闪避，通常有更快的位移速度或者固定位移和无敌帧（可选项，目前为一定时间内有更快的位移速度）。 |

跳跃状态将基础运动流程切割为可独立控制的阶段，便于精确控制各段动画、物理和对外交互。

### 2.2 攻击层（Attack Layer）

| 状态 | 说明 |
|------|------|
| AttackIdle | 攻击层待命，不产生任何覆盖。 |
| NormalAttack1/2 | 普通攻击连段，各段可独立配置前摇、判定窗和后摇。 |
| SkillQ / SkillR | 特殊技能，可能含长前摇、投技、空中可用等标记。 |

攻击层可设计为树状或线性连段，内部状态转换仅由出招逻辑决定，不直接感知基础层和受击层的具体状态（仅通过协调器获取必要信息）。

### 2.3 受击层（Hit Layer）

| 状态 | 触发方式 | 表现 | 后续可转换状态 |
|------|----------|------|----------------|
| Hit | 普通攻击命中 | 短暂僵直，轻微后仰 | Idle（恢复）、Hit（叠加）、Knockback、Launched、Down |
| Dizzy | 重攻击/特定技能 | 原地不动脑袋眩晕 | 同 Hit |
| Down | 累积击倒值/强力击倒/落地 | 倒地，可有无敌帧 | GetUp、Death |
| GetUp | 倒地时间结束 | 播放起身动画，可有无敌 | Idle（归还基础层） |
| Death | 血量归零/致命攻击 | 死亡动画或布娃娃，不再接受输入 | 终态，或复活 |

受击层内状态按反馈严重程度递进，所有状态在血量归零时均可直接切入 Death。

## 3. 层间协调机制

### 3.1 优先级与中断规则

固定优先级：**Hit > Attack > Base**。

采用角色状态协调器（StateCoordinator）统一仲裁，高层状态激活时低层被强制中断或约束：

- Hit 层激活 → 攻击层立刻退出（除非有霸体标记），基础层冻结移动输入并停止主动动画。
- Attack 层激活 → 根据招式配置，可完全锁定基础层移动，或通过 Avatar Mask 保留下半身运动。
- Base 层仅在无更高优先级层霸占时响应玩家输入。

关键的中断响应通过事件驱动，每帧协调器检查各层激活请求并裁决。

### 3.2 动画混合

使用 Unity Animator 多层 + Avatar Mask 实现：

- **基础层**：权重始终为1，控制全身动画，作为默认动画来源。
- **攻击层**：权重要么0要么1，通常带一个仅影响上半身的 Avatar Mask。进入攻击状态时权重新变到1，覆盖上半身动画。
- **受击层**：设置为最高动画层，Avatar Mask 全身覆盖，默认权重0。受击时瞬间将权重设为1，完全屏蔽所有下层动画。

若需要更细粒度控制，可在协调器中使用 Playable API 动态混合不同层的 AnimationClip。

### 3.3 移动与输入控制

每层向协调器输出一个层数据描述，结构中包含该层期望的位移增量、是否遮蔽下层动画、当前动画标识、是否屏蔽玩家输入等字段。

协调器根据当前最高激活层采纳对应的位移和输入屏蔽策略。一般情况下：

- Hit 层：强制位移（击退/浮空），屏蔽所有输入。
- Attack 层：可使用招式自带位移，是否接收方向输入由招式配置决定。
- Base 层：完全由玩家输入驱动移动。

## 4. 跳跃状态设计

跳跃在基础层被细化为三个独立状态，以满足不同阶段的逻辑和动画需求。

### 4.1 JumpStart（起跳）

- **动画**：不可循环的蹬地/蓄力动画。
- **持续时间**：较短（约3~8帧），期间**不可被打断**（除受击外）。
- **逻辑**：进入时施加垂直初速度，禁用移动输入或仅允许微小方向修正。
- **关键事件**：动画中嵌入 `LeftGround` 事件，标记角色实际离地时刻。该事件后 `IsGrounded` 置为 false，受击逻辑据此判断应进入地面受击还是空中受击。

### 4.2 JumpAir（空中）

- **动画**：可循环的浮空姿态，通常基于垂直速度在上升、顶点、下落之间混合。
- **持续时间**：从离地到落地。
- **可交互性**：
  - 可响应二段跳输入，重新进入 JumpStart 或 DoubleJump 状态。
  - 可被攻击层覆盖（空中攻击），此时动画上半身或全身被替换，但基础层状态仍保持 JumpAir。
  - 可被受击层接管（浮空受击），冻结 JumpAir 动画，位移交由受击层控制。
- **落地检测**：每帧检测地面，若着地且无更高层激活，切换到 JumpEnd。若着地时正处于受击状态，则落地事件不由基础层处理，转由受击层切入 Down 状态。

### 4.3 JumpEnd（落地）

- **动画**：落地缓冲动画，可能区分轻落地和重落地。
- **持续时间**：动画完整播放，期间可禁用移动输入或降低移动速度。
- **中断规则**：可被受击层随时打断；通常允许攻击层打断以实现落地取消（需配置允许）。

### 4.4 跳跃与受击的协调要点

- **起跳瞬间受击**：以 `LeftGround` 事件为界，前为地面受击（HitStun/Knockback），后为空中受击（Launched）。
- **空中受击后落地**：协调器判定若 Hit 层仍激活，则进入受击层 Down 状态，基础层不触发 JumpEnd。
- **空中攻击后落地**：默认攻击层状态不因落地自动退出，落地后若攻击仍在继续，自然表现为地面攻击延续。

## 5. Death 状态定位

Death 状态隶属于**受击层**，作为其终态和最高优先级状态。理由如下：

- 语义上死亡是致命伤害的极端反馈，与受击属于同一因果关系链。
- 优先级需要绝对保证：一旦进入死亡，不应再被任何其他状态覆盖。
- 避免污染基础层：基础层仅处理主动运动，死亡不应保留任何输入或移动能力。
- 简化仲裁：Death 天然继承受击层对下层的一切屏蔽规则，无需额外逻辑。

**Death 的约束**：
- 进入后禁用角色控制器、锁定移动、关闭碰撞响应（视需求）。
- 后续伤害事件不再处理。
- 若有复活机制，从 Death 退出即回归基础层 Idle；若无则 Death 为状态机最终停泊点。

## 6. 典型交互流程

### 6.1 奔跑中普攻
1. Base 层处于 Move，驱动移动动画和位移。
2. 攻击输入触发 Attack 层进入 NormalAttack1，通知协调器。
3. 协调器根据招式配置决定是否屏蔽移动，并激活 Animator 攻击层权重（上半身混合）。
4. 攻击结束，攻击层返回 AttackIdle，协调器释放控制，Base 层恢复完全控制。

### 6.2 攻击中途受击
1. 攻击动画播放中，收到伤害事件，Hit 层请求进入 HitStun。
2. 协调器裁决：Hit 优先级最高，立即强制 Attack 层退出，冻结 Base 层，激活受击动画（全身覆盖）。
3. 受击动画播放完毕，Hit 层退出，控制权归还，通常回到 Base 层 Idle 或维持原运动状态。

### 6.3 跳跃攻击后落地
1. Base 层在 JumpAir，玩家输入攻击，Attack 层进入空中攻击技能。
2. 角色落地时，协调器检查：Attack 层仍激活，不做落地切换。
3. 空中攻击动作持续在站立姿态播放，直到攻击结束才归还给 JumpAir（此时已在地面，将快速转入 Idle/Move）。

## 7. 设计总结

本架构以分层的低耦合模块化方式，解决了动作游戏中状态复杂、交互频繁的难题。

- **职责分离，避免状态爆炸**：每层只管理本领域的状态，最终组合出的表现由协调器动态混合，而非硬编码枚举所有复合状态。
- **严格优先级，保证反馈即时**：Hit > Attack > Base 的中断链条确保伤害反馈永远能立即生效，符合动作游戏手感要求。
- **动画与运动解耦**：通过 Avatar Mask 和分层输出结构，实现了上半身与下半身、主动移动与强制位移、玩家输入与系统控制的灵活分割。
- **状态边界清晰**：跳跃三段化、落地归属判断、起跳离地标记等设计，将模糊的时刻划定为明确的逻辑分界，大幅降低边界bug。
- **横向扩展性强**：新增运动方式、攻击技能或受击类型，只需在对应层内添加状态，并遵循现有的协调协议，无需重构全局状态网。
- **调试友好**：每一层的当前状态、拦截情况均可实时可视化，便于快速定位优先级或动画混合问题。

该设计框架适用于典型的动作RPG、格斗游戏和平台动作游戏，可根据项目需求进行裁剪或加深。

## 8. 面向MMORPG的补充与深化设计

### 8.1 状态行为插件化与数据驱动

- **状态配置数据（ScriptableObject）**：每个状态定义为 `StateData` 资产，包含动画标识、过渡条件列表、持续时间、允许中断优先级、自身优先级、进入/退出回调事件等。策划可直接配置新技能或新受击类型，无需修改代码。
- **状态行为接口（IStateBehaviour）**：`OnEnter() / OnUpdate() / OnExit()` 生命周期方法，并用 `StateMachineBehaviour` 或独立组件实现。
- **条件与过渡系统**：过渡条件统一为 `Condition` 基类（如 `BoolCondition`、`FloatThresholdCondition`、`EventCondition`），在协调器中评估，避免硬编码转换逻辑。

### 8.2 韧性、霸体与中断优先级的精细化

固定层级优先级在面对霸体、强控等机制时需扩展为**动态优先级**与**韧性系统**：

- **优先级分级**：每个状态声明 `priority` 整数值与 `interruptGroup`。例如受击轻微硬直优先级80，击倒100，死亡为最高。攻击层中不同招式设定不同优先级，大招高于普攻。
- **霸体/韧性系统**：角色拥有韧性值与霸体标记。当前状态 `protectLevel` 决定能否被更高优先级打断；若攻击状态勾选“无视韧性”或韧性被打空，才可被受击打断。韧性计算由协调器专有模块处理。
- **中断规则修正**：高优先级状态请求激活时，协调器比较当前激活状态的 `priority`、检查韧性条件，裁决是否中断。支持蓄力霸体、技能读条护盾等MMO表现。

### 8.3 网络同步架构

MMORPG的状态机必须支持网络同步：

- **权威模式**：服务器运行逻辑状态机（仅状态ID、关键参数如血量、位置），客户端运行表现状态机（完整动画、混合）。
- **状态同步包**：服务器下发 `StateSyncData`（例如 `baseState = Move, attackState = SkillQ, hitState = none, serverPosition, timestamp`），客户端解析后强制状态切换，并做运动/动画插值。
- **输入上行**：玩家输入封装为命令发送服务器，服务器执行状态转换并广播结果。客户端采用**乐观预测**：先本地播放动画，若服务器纠错则平滑过渡。
- **关键事件对齐**：受击、跳跃离地等判定以服务器为准，`LeftGround` 事件由服务器物理判定产生，同步给客户端。

### 8.4 扩展基础层状态（后续实现）

> 此部分将在后续版本中实现，包括但不限于交互、骑乘、游泳、攀爬、坐下等非战斗运动状态。这些状态将遵循相同的分层协调规则。

### 8.5 攻击层细化：吟唱、蓄力与引导

MMO常见的施法类型需在攻击层内引入**子状态机**：

- **吟唱（Channeling）**：可移动或定身，持续引导产生效果。
- **蓄力（Charge）**：按下蓄力，松开发射，期间移动受限。
- **读条（Casting）**：不可移动，进度条走完触发效果，被打断则失败。

攻击层内部可设计 `ChargeStart → Charging → ChargeEnd` 或 `Casting → (打断) → Idle` 等子流程，移动限制与动画混合通过协调器与基础层交互。

### 8.6 死亡与复活流程深化

受击层Death需适配MMO逻辑：

- **Death子态**：`DeathPose`（死亡姿势）→ `GhostMode`（灵魂状态，可移动但无碰撞）。死亡后控制权转至Ghost基础层，坐标可回归复活点。
- **复活**：`Resurrect` 事件中断Death，播放复活动画，恢复角色控制器，回归Idle。协调器清空所有状态，重置基础层。
- **布娃娃与性能**：仅在需要时开启布娃娃，多数情况使用动画死亡，以减少网络带宽与CPU开销。

### 8.7 整合Unity Playable API - 动画混合建议

对于复杂MMORPG，建议**全面采用Playable API**：

- **分层混合树**：构建 `AnimationMixerPlayable` 堆栈，分别为 BaseLayer、AttackLayer、HitLayer 及额外层。每层根据配置输出权重。
- **动态Mask**：运行时创建 `AvatarMask` 或动态设置骨骼权重，通过 `AnimationLayerMixerPlayable` 实现精确混合。
- **优势**：更轻量、可帧级控制权重，易于整合程序化叠加（如受伤晃动）。避免 Animator Controller 多层耦合的维护难题。

### 8.8 可视化调试与编辑器工具

- **协调器运行时窗口**：利用 `OnGUI` 或 EditorWindow 实时显示各层当前状态、优先级锁定、活跃过渡及动画权重。
- **状态机可视化**：基于 Unity GraphView 编辑状态与过渡，预览动画，生成 ScriptableObject 配置，提升策划产能。
- **游戏内状态快照**：记录最近几次状态切换日志，便于复现BUG。

### 8.9 事件总线和解耦

各层状态机与外界（UI、音效、战斗统计）通信应通过**事件总线**：

- 状态进入/退出时抛出 `EntityStateChangeEvent`（entityId, layerType, prevState, newState）。
- 受击、跳跃、死亡等独立事件，方便成就、任务、队伍框架等模块监听，避免硬引用。
- 事件总线可使用 `ScriptableObject` Event 通道或 C# event 包装，保持高性能。

### 8.10 性能与对象池

MMORPG同屏角色数量大，状态机实例需优化：

- 使用预分配的状态行为数组，避免每帧分配新对象。
- 采用 `EntityCommandBuffer` 风格延迟状态切换，集中处理以防止重入和帧内状态抖动。
- 动画 Playable 的创建使用对象池，复用 `AnimationClipPlayable`，减少资源开销。

## 9. 补充后的整体流程

1. 服务器逻辑状态机裁决战斗，生成 StateSyncData 下发。
2. 客户端协调器接收同步数据，结合本地预测，运行三层状态机并进行动画混合。
3. 玩家输入经本地验证（或服务器验证），尝试转换状态，经协调器优先级检查、韧性计算后激活新状态。
4. 各层状态行为通过组件化执行位移、物理、特效、音效等，并发送事件。
5. 全局事件总线将状态变化分发至UI、其他玩家显影、任务系统。
