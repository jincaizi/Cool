# PvP、服务端复活、远程真角色与倒地表现 设计

> 面向 AI 代理的工作者：本规格续接 `2026-10-07-webgl-interview-demo-design.md`。读完本文件后用 `superpowers:writing-plans` 生成实现计划。

**目标（一句话）**：让面试官（手机浏览器）与开发者（PC）在同一个世界里**互相能打死对方**，死亡与复活在**两端都看得见**，且真人玩家渲染成真角色。

## 1. 目标与成功判据

### 目标

1. 面试官与你**互相能造成伤害**，伤害由服务端裁决（沿用 F1）
2. 任一方死亡后：**两端**都能看到对方**倒下 → 躺 8 秒 → 起身 → 满血**
3. **100 个 bot 同样能被打、会死、会复活**（人类裁定：不做"绝缘人群"）
4. **真人玩家渲染成真角色**（含倒地/死亡/起身动画）；**bot 与怪物保持占位**（人类裁定：避免 100 个蒙皮网格压垮手机）

### 成功判据（这就是"完成"的定义）

- 浏览器端与 PC 端互殴能扣血；被击者的血条在**攻击方**的屏幕上同步下降
- 击杀发生后：**两端**都看到倒下、躺 8 秒、起身、满血
- bot 被打死会倒下、8 秒后复活，且**复活前后都仍计入 AOI 可见集合**
- 真人在对方屏幕上**看得清是角色**（不是胶囊），且能看到对方的倒地/死亡/起身
- 回归：EditMode / Server.Tests / PlayMode（三配置并集）全绿；WebGL 出包成功

## 2. 范围边界

### 做

| 层 | 内容 |
|---|---|
| **协议** | 实体**存活状态**；**玩家侧** `ActionState`；**真人 / bot 判别**。三者一次改完 |
| **服务端** | `PlayerState.Respawn()`；主循环的死亡计时（8 秒）；快照组装带上存活与动作状态 |
| **客户端 · 表现层** | `HitFSM` 的 `Death` / `Down` / `GetUp` 补**入边转移**；由**服务端状态**驱动；联网下死亡期间的输入门禁 |
| **客户端 · 渲染** | `RemoteEntityRegistry` 按判别分支：真人 → 角色预制体 + Animator；bot / 怪物 → 保持占位 |

### 明确不做

- **击退与浮空**（`Knockback` / `Launched`）——状态不存在、无专门素材、要空中物理。人类已裁定
- **竞技场 / 分阵营 / 匹配 / 计分板**——"你和他对打"不需要
- **服务端权威的格挡减伤**（P4 backlog，D-P4-8 登记）
- **远程玩家的名字板**——现有名字板系统另论，本设计不碰
- **包体清理**（人类裁定"最后再做"）
- **P7 打怪升级**——本次不选

## 3. 架构

```
[协议层]  EntitySnapshot 扩展
    ├─ Alive            实体是否存活（服务端权威）
    ├─ ActionState      对**玩家**也开放（现在恒 0）
    └─ 判别             真人玩家 / bot / 怪物
          ↓
[服务端]  PlayerState.Respawn()  +  主循环死亡计时（8s）
    死亡与复活经由**既有快照链**被观察者看到（不新增消息）
          ↓
[客户端]  ┌ 本地玩家：ApplyServerDamage 的权威余血驱动死亡表现；服务端回血驱动起身
          └ 远程实体：快照里的 Alive/ActionState 驱动倒/死/起；按判别选择渲染分支
```

### 为什么"判别"必须在协议层

客户端要靠它决定**渲染成什么**（F6/F7）。而唯一现成的替代是 **bot 的 id 范围**（`BotRunner` 从 1,000,000 起）——那是个魔数，任何一个新 id 分配方都会打破它。放在协议里是一次性成本。

### 为什么死亡必须由服务端驱动

F10：联网下客户端**有意**不做本地判死。若本设计让客户端自己判，就会与既有的 D-P6-15/18 冲突，并重新引入"两端不一致"的可能。

## 5. 错误处理

| 场景 | 处理 |
|---|---|
| 观察者进场时目标已经死了 | 首次快照就要带 `Alive=false`，远程视图直接进入倒地姿态——**不能只在"死亡那一刻"的增量里发** |
| 观察者错过了复活那一帧 | 复活同样是**状态**而非事件：任何一帧的快照都能把视图从倒地纠正回站立 |
| 死亡期间收到该实体的移动 | 服务端已停止其移动；客户端对 `Alive=false` 的实体不应用位移插值 |
| 本地玩家死亡期间的操作 | 沿用 P6 的输入门禁语义（D-P6-21/22 系），**联网下由服务端余血驱动** |
| bot 被大量同时击杀 | 复活的计时器是每实体一个 tick 计数，**不引入每帧遍历全表**的额外开销 |

## 9. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| **D-1** | **协议一次改完**：判别 + 存活 + 动作状态同批 | 三次动协议 = 三次重出包 + 三次重验。三者服务同一个目标 |
| **D-2** | 服务端复活 **8 秒**（人类裁定，两轮确认：先"5 秒或更长"、再选定 8），且**服务端权威** | 与单机 3 秒（F9）刻意不同——对打时死亡要有分量（比单机的 3 秒长得多）。**它是一个常量**，演示时可调 |
| **D-3** | bot 与真人**共用同一条**伤害与复活路径，只在**渲染**上分叉 | F1/F8：服务端已经把他们当同类。分成两条路径会让每条新规则都要改两处 |
| **D-4** | 真人 / bot 判别放在**协议层**，不用 id 范围。**具体编码：`EntityKind` 增加一个值 `PlayerBot = 2`**（现为 `Player = 0` / `Npc = 1`），`BotRunner` 注册时用它 | id 范围是魔数（F8），任何新的 id 分配方都会打破。**复用一个既有的判别字段比新增一个 bool 更省**——客户端与快照链都已经在传 `Kind` |
| **D-5** | 死亡表现由**服务端状态**驱动，不做客户端预测 | F10：联网下客户端有意不判死（D-P6-15/18）。预测会把那个决定推翻 |
| **D-6** | 不做击退与浮空（人类裁定） | 状态不存在、无专门素材、要空中物理——本次三块里最贵的一步，收益是观感 |
| **D-7** | 真角色模型**只给真人**（人类裁定） | R2：`--bots 100` 是 P3 的演示前提，100 个蒙皮网格在手机上不可行 |
| **D-9** | **复活用一条点对点消息通知本人**（`RespawnNotice`，战斗段 300-399），而不是指望快照 | F11：本地玩家不在自己的快照里——没有这条消息，被复活的人会永远停在死亡画面（`TickRespawn` 在联网态被短路正是为了防它站起来而服务端还当他死了） |
| **D-8** | **不改 PvP 的裁决规则**（F1 已现成） | 改一个已经在工作的东西只会引入风险。本设计只把它**接到表现层** |
