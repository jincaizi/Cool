Self-Review: AIBrain & State Machine — 6 Issues Found

Critical re-examination of the proposed design. 3 issues require structural changes.

Issue 1: Update Order Bug

// ORIGINAL PROPOSAL (wrong order):
_behaviours.UpdateActive(_ctx);   // Updates behaviour for OLD state
_fsm.Update(_ctx);                // Transitions to NEW state, runs OnUpdate
// → Behaviour got updated for the wrong state this frame!

// FIXED ORDER:
_fsm.EvaluateTransitions(_ctx);   // 1. Check transitions (may change state)
_fsm.ExecuteState(_ctx);          // 2. Run OnUpdate for CURRENT state
_behaviours.UpdateActive(_ctx);   // 3. Update behaviour for CURRENT state

Issue 2: IAIBehaviour Adds Complexity, Little Value

Each behaviour maps 1:1 to a state (DefendBehaviour ↔ Defend, TauntBehaviour ↔ Taunt). The extra interface + scheduler layer creates the exact bug it's trying to prevent (forgetting to call Update).

Fix: Merge behaviour into state

  • DefendState contains block counting, cooldown, counter logic
  • TauntState contains random trigger logic
  • FSM guarantees OnEnter/OnUpdate/OnExit are always called
  • Eliminates IAIBehaviour + BehaviourScheduler entirely
  • Bug class "forgot to call Update()" becomes impossible

What we lose

  • Can't hot-swap behaviours at runtime (never used)
  • Can't share behaviour across states (never used — each is 1:1)

Issue 3: Global Transition Priority Unclear

Death must interrupt ANY state. Who checks it — each state individually, or the FSM globally?

// FIX: AIStateMachine checks global transitions first, then delegates to state
public void EvaluateTransitions(AIContext ctx)
{
    var next = CheckGlobalTransitions(ctx)      // Death, future: phase change
            ?? _currentState.EvaluateTransitions(ctx);
    if (next != null) TransitionTo(next, ctx);
}

private AIStateBase CheckGlobalTransitions(AIContext ctx)
{
    if (ctx.Stats.IsDead && _currentState.StateType != MonsterAIState.Death)
        return GetState(MonsterAIState.Death);
    // Future: check boss phase override here
    return null;
}

Issue 4: Attack Sub-States Need Animation Callback

The current code fires damage on state entry. The fix requires animation events to drive the Windup → Active → Recovery transitions. But the animation callback (StateMachineBehaviour) runs on the Animator, not on AIStateBase.

// AttackState exposes a callback that the Animator StateMachineBehaviour calls:
public class AttackState : AIStateBase
{
    // Called by AttackStateBehaviour.OnStateEnter via AIBrain reference
    public void OnAnimationAttackWindow()
    {
        _shouldResolveDamage = true;  // Damage resolved in next OnUpdate
    }
}

→ AIBrain holds a reference that StateMachineBehaviour can access via the Animator's GameObject → MonsterEntity → AIBrain → current AttackState.

Issue 5: State Instance Lifetime

Created once in AIStateMachine constructor and reused — zero allocation during gameplay. Each OnEnter must fully reset state (clear timers, reset flags). This is a convention, not enforced by code — document it clearly.

Issue 6: Defend → Counter Attack Flow

Current code: Defend state exits → Attack if counter ready OR if target in range.

With merged DefendState, this logic lives in DefendState.EvaluateTransitions(), which has direct access to block count, timer, and target distance. Simpler and more cohesive than routing through a separate DefendBehaviour.
